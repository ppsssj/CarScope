# P13-D 다중 부품 AI 외관 분석 통합

엔진룸 부품 6개 모두에서 모바일 점검 화면의 AI 외관 분석을 쓸 수 있게 했다. 탐지가 되는 4개는 Roboflow 후보에서, 탐지가 안 되는 2개는 사람이 직접 지정한 영역에서 시작하고, 둘 다 같은 Crop → 동의 → 분석 → 결과 경로를 쓴다.

- 기준: `main` `ce6f0ee`(P13-A~C 병합 후), 브랜치 `feat/p13-d-multipart-vision`
- **실제 OpenAI·Roboflow 호출 0회**(원장 4/5, 19/20 그대로). 모든 E2E는 고정 탐지기와 부품별 MOCK이다. **정확도 주장 없음.**
- 운영(Render)은 바꾸지 않았다. 실제 휴대폰에서 쓰려면 9절의 승인과 설정이 필요하다.
- 증거: [evidence/p13-d/README.md](evidence/p13-d/README.md)

## 1. 점검 부품 전체와 사진 AI 적합성

| 영역 | 부품 (QR task) | 이번 AI 분석 | 사진으로 볼 수 있는 것 | 사진 AI로 확정하지 않는 것 |
|---|---|---|---|---|
| 엔진룸 | 워셔액 주입구 (`washer-fluid`) | **탐지 + 분석** | 캡 존재·닫힘·외관 손상 | 워셔액 양, 펌프·노즐 작동 |
| 엔진룸 | 일반 냉각수 리저버 (`coolant-reservoir`) | **탐지 + 분석** | 리저버 식별, MIN/MAX·액면 가시성, 외관 파손·누출 흔적 | 가려진 액면, 저전도와의 구분(표기 없이), 냉각 계통 작동·농도 |
| 엔진룸 | 브레이크액 리저버 (`brake-fluid`) | **탐지 + 분석** | 리저버 식별, 액면·MIN/MAX, 누출·파손 흔적 | **제동 성능·주행 안전**, 액 품질·수분 |
| 엔진룸 | 퓨즈박스 (`fuse-box`) | **탐지 + 분석** | 하우징·커버 식별, 커버 누락·개방, 외관 파손 | 내부 퓨즈·릴레이, 전기 계통 |
| 엔진룸 | 12V 보조 배터리 (`battery-12v`) | **직접 지정 + 제한적 분석** | 12V로 확인 가능한지, 케이스 손상, 누출, 보이는 단자의 부식 | **충전 상태·전압·수명**, 고전압 계통, 탈거·단자 조작 |
| 엔진룸 | 저전도 냉각수 리저버 (`lcw-coolant-reservoir`) | **직접 지정 + 제한적 분석** | 표기로 식별 가능한지, 액면·MIN/MAX, 파손·누출 | 표기 없는 구분, **성분·농도·전도도**, 보충·정비 지시 |
| 타이어 | 앞·뒤 좌·우 (`tire.*`) | 없음 | (후속) 트레드·측면 외관 | **공기압**, 마모 한계 수치 |
| EV | 충전구 (`ev-charge.port`) | 없음 | (후속) 이물·덮개 | 고전압 안전, 충전 기능 |
| EV | 고전압 배터리 팩, 충전구 덮개 | 없음(QR task 없음) | | **고전압 계통 안전 일체** |
| 와이퍼 | 좌·우 (`wiper.front.*`) | 없음 | (후속) 블레이드 외관 | 닦임 성능 |
| 등화 | 하향·상향 좌·우 (`light-*`) | 없음 | (후속) 렌즈 균열 | 점등 여부(차량 작동 필요) |

이번 범위는 엔진룸 6개다. 나머지는 사진 AI를 붙이지 않았고 기존 점검만 쓴다.

## 2. 탐지와 분석의 분리

| 표 | 함수 | 뜻 |
|---|---|---|
| `PART_DETECTION` (P12-E, **변경 없음**) | `offersDetection()` | Roboflow가 영역 후보를 낼 수 있는가. 실험 4 / 미지원 2 / 검증 0 |
| `ANALYSIS_PROFILES` + `ANALYSIS_SUPPORT` (P13-D) | `offersAnalysis()`, `regionAllowed()` | Vision 분석을 제공하는가, 어떤 영역 출처를 받는가 |

| 부품 | 탐지 상태 | 분석 상태 | 영역 출처 | 근거 |
|---|---|---|---|---|
| 워셔액 | EXPERIMENTAL | EXPERIMENTAL | AI 후보, 직접 지정 | 실제 호출 4회(사진 2장), 정확도 미확인 |
| 냉각수 · 브레이크액 · 퓨즈박스 | EXPERIMENTAL | EXPERIMENTAL | AI 후보, 직접 지정 | MOCK만 |
| 12V · 저전도 | **UNSUPPORTED (그대로)** | EXPERIMENTAL, **제한적** | **직접 지정만** | MOCK만 |

- 서버는 탐지 미지원 부품에 `AI_CANDIDATE` 영역이 오면 400으로 거부한다. 사람이 지정한 영역만 받는다.
- 서버는 계속 QR 제출 토큰의 점검 task와 부품이 맞는지 확인한다. 다른 부품이면 403이다. 6개 부품 모두 시험했다.
- `VERIFIED`는 어디에도 없다.

## 3. 사용자 흐름

```text
점검 화면 ── 'AI로 부품 위치 찾기 · 실험' (탐지 부품)
          └ 'AI로 부품 상태 보기 · 실험'   (12V, 저전도)
   탐지 부품: Roboflow 동의 → 사진 → 후보 표시 ─┐
   직접 지정: 사진 (어디에도 보내지 않음) ──────┤
                                               ▼
        공통: 영역 선택/직접 지정 → 잘라낸 사진 미리보기 → Vision 동의(서비스 이름)
              → 분석(취소 가능) → 관찰·의심·판단 한계·재촬영 → "직접 확인할게요" → 기존 점검
```

- 직접 지정 부품에는 Roboflow 동의 체크박스가 아예 없다. 사진을 고를 때 탐지 요청은 0건이다(브라우저 시험).
- 제목에 "직접 지정, 제한적 분석"과 "실험 기능이에요. 실제 사진으로 확인하지 않았어요"를 보여 준다. 워셔액은 "실제 사진 2장으로 동작만 확인했고, 얼마나 맞는지는 아직 몰라요"다.
- AI를 쓰지 않거나 분석이 실패해도 기존 체크리스트는 그대로다. AI 결과는 답변에 자동 입력되거나 차량으로 보내지지 않는다(6개 부품 모두 시험).
- 탐지 실패 시 직접 지정, 재촬영, 그림 안내 복귀(P13-A 그대로).

## 4. 부품별 분석 프로파일

P13-A 결과 계약(9개 필드)과 검증기를 그대로 쓴다. v2 스키마는 강제하지 않는다(P13-C 제안은 평가 전용 유지). 워셔액 프로파일과 프롬프트는 바꾸지 않았다.

| 부품 | 식별 규칙 | 의심 코드 | 서버가 거부하는 주장(예) |
|---|---|---|---|
| 냉각수 | 표기가 없고 저전도 통이 있을 수 있으면 `UNCERTAIN` | 액면 MIN 아래, 누출 흔적, 리저버 손상 | "냉각 계통이 정상", "농도가 적정" |
| 브레이크액 | 클러치·파워스티어링 통과 구분 | 액면 MIN 아래, 누출 흔적, 리저버 손상 | "제동 성능이 충분", "수분 함량 N%", "품질이 좋음" |
| 퓨즈박스 | 배치도 표시 등이 없으면 `UNCERTAIN` | 커버 누락, 커버 개방, 커버·하우징 손상 | "퓨즈는 모두 정상", "전기 계통 문제 없음" |
| 12V | 주황 케이블·고전압 표시는 절대 12V가 아님. 표기·단자로 확인 못 하면 `UNCERTAIN` | 케이스 손상, 누출 흔적, 단자 부식 | 전압 수치, 충전 상태·수명, "탈거", "단자를 풀어", "점프 시동" |
| 저전도 | **표기로만** 식별. 색·모양·위치로는 금지 | 액면 MIN 아래, 누출 흔적, 리저버 손상 | "전도도가 낮음", "농도 적정", "교체하세요" |

- 공통 규칙(P13-A)은 그대로다: 정상·안전 단정 금지, 부품 조작 권유 금지, 식별이 불확실하면 `INDETERMINATE`, 근거 없는 이상 금지.
- 부품별 금지 주장은 서버와 화면이 같은 검증기로 확인한다(`FORBIDDEN_CLAIM`). "충전 상태와 전압은 사진으로 알 수 없습니다"처럼 판단 불가를 말하는 문장은 허용된다(시험).
- 직접 지정 부품의 프롬프트에는 "사람이 지정한 영역이고 탐지기가 제안하지 않았다"가 들어간다.

## 5. 서버·보안

P13-A 중계를 그대로 쓴다: 서비스별 동의 헤더, QR 토큰, task·부품 일치, `CLAIMED` 상태, JPEG만 2MB·64~2048px, 45초 시간 제한, 휴대폰당 진행 중 1건, 분·세션 호출 상한, 응답 계약 검증, 상류 오류 미노출, 연결 끊김 시 공급자 취소. 키는 서버의 공급자 안에만 있고 브라우저는 자기 출처만 부른다.

## 7. 실제로 분석 가능한 범위와 불가 범위

- **가능(실험):** 6개 부품의 사진에 보이는 외관. 부품 식별 여부, 표시·액면의 가시성, 뚜렷한 파손·누출·부식·커버 상태의 **의심**.
- **불가(사진 AI로 확정 안 함):** 액면이 가려진 경우의 정상 여부, 냉각·제동·전기 계통의 작동, 액체 성분·농도·전도도·품질, 배터리 전압·충전·수명, 내부 퓨즈, 고전압 계통 안전, 타이어 공기압.
- **모름:** 실제 사진에서의 정확도(워셔액도 2장뿐). 12V와 저전도는 표기가 안 보이면 대부분 `INDETERMINATE`가 될 가능성이 높다. 화면에 그렇게 안내한다.

## 9. 실제 휴대폰 사용을 막는 항목 (승인 필요)

지금 실제 휴대폰은 Render(`render-stateful.mjs`)로 접속한다. 그 경로에서는 AI가 **의도적으로 꺼져 있다**. 정적 게이트 `PART_DETECTION_OFF`, `PART_ANALYSIS_OFF`가 막는다. 로컬 실험 서버는 127.0.0.1에만 열려 휴대폰이 접속할 수 없다.

| # | 막는 항목 | 필요한 것 |
|---|---|---|
| 1 | Render 진입점이 AI를 켤 수 없음 | 별도 실험 진입점(예: `render-vision-experiment.mjs`)과 `startRenderStateful`의 `partAnalysis` 인자. 두 OFF 게이트를 "그 진입점에서만 허용"으로 바꾸는 **보안 정책 변경 승인**(WebXR 실험 진입점과 같은 방식) |
| 2 | 공급자 코드가 Render 코드 그래프 밖(`tools/vision-poc`) | 그 진입점에서만 OpenAI 어댑터(와 Roboflow 클라이언트)를 쓰도록 배치하고 게이트 검사 범위를 맞추는 작업 |
| 3 | 운영 키와 설정 | Render 비밀 변수 `OPENAI_API_KEY`, `OPENAI_VISION_MODEL`(필요 시 Roboflow 키). `ENV_CANNOT_ENABLE_AUTH` 허용 목록 갱신. **소유자가 직접 등록** |
| 4 | 유료 호출 상한 | 지금 원장은 로컬 파일 5회다. 운영에는 서버 측 일/월 호출 상한(Postgres 집계 등)과 초과 시 503이 필요하다. 세션당 상한(10분 6회)만으로는 부족하다 |
| 5 | Roboflow 운영 사용 | P12-F의 남은 승인(모델 라이선스, 학습 데이터 권리, 이미지 처리 조건)이 풀리지 않았다. **풀리기 전에는 탐지 없이 시작하는 선택지**가 있다. 6개 부품 모두 직접 지정으로 분석하는 방식이다. 지금 서버는 분석에 탐지를 요구하므로(`PART_ANALYSIS_NEEDS_DETECTION`) 이 규칙을 바꾸는 결정이 필요하다 |
| 6 | 외부 전송 조건 | OpenAI 계정의 데이터 사용·보관 조건 확인, 개인정보 안내 문구의 법무 검토 |
| 7 | 실기기 | Z Flip 등에서 촬영·동의·취소·화면 크기·시간 확인 (`NOT_RUN`) |

1~4와 6은 코드 또는 설정으로 할 수 있지만 **운영 보안 정책과 비용을 바꾸므로 이번에 수행하지 않았다.** 승인되면 1~4가 다음 구현 과제다.
